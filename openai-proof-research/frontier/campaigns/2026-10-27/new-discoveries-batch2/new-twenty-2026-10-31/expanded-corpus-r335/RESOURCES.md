# Resource accounting and exceptions

First actual command: timeout 20 python3 -I -B <lane>/bootstrap.py. Its untouched bootstrap-receipt.json records its own caps and exit. Every subsequent shell command used timeout 140 and Python -I -B; each Python job set affinity to the first two allowed CPUs, RLIMIT_CPU=120 seconds and RLIMIT_AS=6 GiB before any task/source file read. pdftotext child processes inherited affinity and limits and were synchronously waited/reaped. The source-download batch used two network worker threads; no mathematical job was executed.

Managed exec terminal results supply actual exit code and wall time for early jobs. Early one-shot commands did not persist per-job telemetry into jobs.jsonl; this is a logging limitation, not an invented clean group audit. The retrospective early-job record lists their actual task and exit based on returned terminal results, without fabricating RSS/CPU measurements. Later fetch.py jobs persist argv/caps/self/children rusage and completion in jobs.jsonl. The first download batch printed self ru_maxrss=29712 KiB, user CPU 0.081755s/system 0.026271s, with reaped-child CPU 1.000538s/0.076697s. Those are SELF and reaped-child observations, not a sampled process-group/cgroup/service peak. Per-process limits do not establish an aggregate process-group memory limit. No group/cgroup/service telemetry was available or claimed.

Resource exceptions: no aggregate/group memory telemetry; early per-job logs only in managed terminal with retrospective file summary; the 15 MB book fetch hit the source-byte cap and produced an incomplete PDF (pdftotext exit 1), fully reaped. No timeout/kill of a mathematical worker was needed. No background job remains: sessions 59734, 34961, 51545, 90890 and 84906 all returned actual exit 0; their pdftotext statuses are recorded separately, including the one failure. A Python job exit 0 does not turn a 403/404/conversion failure into source success.
