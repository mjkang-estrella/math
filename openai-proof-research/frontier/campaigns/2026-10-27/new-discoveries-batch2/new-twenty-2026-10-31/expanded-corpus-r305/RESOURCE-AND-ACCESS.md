# Resource and access receipt

First command: shell ulimit CPU 120 seconds and address space 2 GiB, with a 20-second timeout, but `taskset -pc $$` queried affinity rather than setting it. This violates the explicit first-command affinity requirement. No claim of full first-command compliance is made. The shell/timeout wrappers were not independently affinity-capped. Initial calls have tool duration/exit receipts in conversation, not a saved per-process telemetry log. The initial AGENTS/reservation/allowlist output was truncated; literal statements were subsequently reread separately without truncation.

Subsequent Python processes set their affinity to the first two CPUs in their inherited available set, inside the limited process; CPU and AS limits were set before task work. Early setup commands used 25–35 second CPU limits, 1–2 GiB AS, and 30–40 second wall timeout. The reusable run.py uses CPU 120 seconds, AS 6 GiB, and an external timeout of 140 seconds with kill-after 3 seconds. AS caps limit possible RSS; process-log.jsonl records getrusage peak RSS and total self CPU, not sampled continuous RSS. The timeout/wrapper itself is not included in Python telemetry.

One run.py /dev/stdin attempt consumed stdin while checking the path and executed no task body; a later run had a variable-name collision in its finally telemetry block after completing history extraction. That run's log was not written. Both exited and were reaped; no scientific work was lost. The wrapper was corrected to execute stdin in a separate namespace. An absent bs4 import failed once; a standard-library HTML parser was used afterward. These failures and early setup processes lack the later uniform per-process log; resource limits still applied except the disclosed initial affinity error.

HTTP used two threads per bounded process, per-request 8–12 second timeouts, and 5–6 MB body bounds. All fetch pools were joined. No detached workers or background shell jobs were created. All exec sessions were collected to exit. Managed web search was used twice for bounded source discovery; its service-side affinity/CPU/RSS/bytes/hashes are unavailable, and no local telemetry is invented for it. Exact retrieved HTML bytes with UTC, status and hashes are in http-receipts.json; error response bodies were not preserved and were not retried to obtain hashes.

Access failures: old LeanPool projects.yml 404; initially guessed Palomar hostname DNS failure; authoritative landing link subsequently identified on LeanPool and read. Its official recent.json returned 403 and that route was stopped. No GitHub API requests, denied-route retries, alternate API substitutes, authentication, TLS disabling, browser tabs, contacts or account actions occurred. Source text and raw corpus records were processed; no mathematical enumeration, numerical search, solver, Lean execution, children, git, shared writes or protected-lane reads occurred.

History scope: exactly the 263 files named in this lane's refreshed allowlist were read, plus permitted ancestor AGENTS/root ledger/STATUS/prior-campaign metadata and source-catalogue metadata. No campaign-wide recursive scan. History files were not copied; only hashes and matched excerpts/entries retained. Initial substring hits can occur inside unrelated SHA strings; history-exact-record-matches.json filters by parsed record ID or exact source_url. No source/proof file was followed into any historical or active crown lane. No protected crown lane was listed, hashed, read or polled.
