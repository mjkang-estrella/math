# Resource and access accounting

First actual command was exactly the requested timeout 20 Python -I -B bootstrap, exit 0. The existing bootstrap-receipt.json has been preserved. Subsequent local Python jobs set affinity to the first two allowed CPUs, RLIMIT_CPU=120 and RLIMIT_AS=6 GiB before input/source reads, under timeout 140. Two pdftotext children inherited those limits and used subprocess timeout 30; both returned exit 0 and were synchronously reaped. No process was intentionally detached.

resource-log.jsonl reports self ru_maxrss (KiB on this Linux host), not group, cgroup, tool-service, or simultaneous parent+child RSS. No group/cgroup or continuous RSS measurement was obtained, and no such compliance claim is made. CPU affinity and address-space ceilings are actual OS limits. Network receipt timestamps are UTC. HTTP was public GET only, with default certificate validation; there was no browser, cookie, authentication, POST, challenge bypass or denied-host retry. Redirects performed by urllib were ordinary public GET redirects, recorded by final URL. One org projects.yml GET returned 404; it was not retried. The distinct Vilin97 and LeanPool heads were kept separate.

Actual exceptions/corrections: the first large read's output was truncated (exit 0), so TASK was reread completely in a subsequent bounded call. The first extraction used the wrong relative corpus ancestor and found zero chunks (exit 0); the corrected exact corpus path produced all 20 records. No partial evidence was counted from that attempt. The optional bs4 import failed with ModuleNotFoundError (exit 1); no package/dependency was installed. Standard-library HTMLParser replaced it. An initial regex text rendering could drop math containing less-than signs; all 11 initial article text files were regenerated using a math-alttext-aware parser before final analyses. Some tool outputs were truncated; relevant passages were reread in narrower excerpts. No truncated display was called a full-body read.

Early process exits, as returned by exec_command: bootstrap 0; initial task/reservation read 0; first extraction 0; corrected extraction 0; runtime creation 0. Later runtime returns are logged, including the import failure; source-processing commands returned normally after that failure. The outer tool's exit reports are authoritative for process termination; Python finally logs record Python outcomes, not invented waitpid data. The pdftotext invocation for sequence-2013 returned 0 as displayed in its tool receipt; the parking conversion child additionally has a resource-log row. The utility-creation and final-manifest processes obey the same caps but are documented here rather than falsely presented as having continuous process telemetry.

The runtime itself does not launch any background work. Every tool invocation completed with an exit code, no PTY/session ID or live exec cell. All descendants launched by this task (the two synchronous text converters) were waited. No claim is made about unrelated jobs on the shared machine.
